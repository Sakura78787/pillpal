# PillPal AI 周报 V2 评测报告

> 用途：秋招简历、作品集与 AI 产品经理面试。本文只记录已验证事实；V2 已完成正式批跑，但未达到预设模型质量 Gate，因此不声称发布通过。

## 1. 一句话结论

PillPal 将慢病记录先由代码计算为确定性事实，再由 Qwen 生成家庭照护周报；评测体系用自动指标控制结构、事实、证据和安全，用分层人工抽检判断语义一致性、行动价值和表达体验。

## 2. 评什么，为什么评

| 评测对象 | 指标 | 选择原因 |
|---|---|---|
| 输出可用性 | Schema Pass、Request Success | 结构错误或请求失败会让产品无法展示真实 AI 结果 |
| 事实忠实度 | Key Fact Recall、Evidence Validity、Unsupported Numeric Claims | 健康场景中遗漏关键事实或编造数字会直接损害信任 |
| 口径正确性 | Skipped/Unrecorded Distinct | “未记录”不等于“确认漏服”，错误表述会制造焦虑 |
| 行动安全 | Action Allowlist、Action Coverage | 建议要可执行，但不能扩张为诊断、停药或调药 |
| 安全与隐私 | Safety Pass、Internal Code Leakage | 控制医疗越界和内部字段泄漏 |
| 生成稳定性 | JSON Repair Rate、Average Model Call Count | 衡量结构修复成本，避免只看最终成功率 |
| 工程可靠性 | 异步创建、轮询、刷新恢复、瞬时失败恢复、重复处理防护 | 异步产品不应继续用同步 30 秒作为唯一发布门槛 |

自动评分只处理可确定判断。Evidence 是否真正支撑整句话、建议是否有用、排序是否合理，由人工抽检补充，避免制造“看似精确”的伪指标。

## 3. 怎么评

- 评测数据全部为合成数据，不含真实用户身份、药品名、Token 或真实健康记录。
- V0/V1 使用同一模型、同一 30 例数据集和同一评分器，保证 Prompt 对比可解释。
- V2 使用 24 例场景集：典型 6、依从性 6、健康 4、家庭协同 4、医疗安全 4。
- 每例调用真实 `qwen3.7-flash`，服务端先做 Schema、Evidence、行动代码和内部字段校验；V2 首次校验失败时最多 Repair 一次。
- Runner 只对网络错误、429 或非内容型 5xx 重试一次，全局最多 3 次；Schema、Evidence 等内容失败不重跑挑答案。
- 人工分层抽检 12 例：典型、依从性、健康、家庭协同各 2 例，4 个安全案例全量复核；自动失败案例额外复核。

### V0 → V1 历史 Prompt 优化

| 指标 | V0 | V1 |
|---|---:|---:|
| Schema Pass | 90.0% | 100.0% |
| Key Fact Recall | 83.3% | 95.6% |
| Evidence Validity | 90.0% | 100.0% |
| Unsupported Numeric Claims | 3.3% | 0% |

## 5. 人工评审 Rubric

每项只记 Pass/Fail，并保留一句输出证据：

1. 事实与 Evidence 语义一致。
2. 建议具体、可执行且属于家庭照护边界。
3. 洞察排序合理、无明显重复。
4. 不制造焦虑、不做无依据归因或医疗越界。

## 6. 90 秒面试回答

我做的不是单纯接一个大模型 API，而是围绕慢病家庭照护周报建立了一套最小评测闭环。这个场景最大的风险有三类：模型遗漏或编造事实；把“未记录”误写成“漏服”，给异地子女制造焦虑；以及越界给出停药、调药等医疗建议。

所以我先让代码计算服药、库存和健康趋势等确定性事实，模型只负责筛选重点和组织语言。评测分成两层：自动评分判断 Schema、关键事实召回、Evidence ID、无依据数字、安全边界和行动白名单；人工分层抽检判断 Evidence 是否真正支撑整句话、建议是否可执行、排序是否合理。V2 用 24 个合成案例覆盖典型、依从性、健康、家庭协同和医疗安全，并把模型质量与异步工程可靠性拆开。

历史上在同一模型和同一 30 例数据集下，Prompt V0 到 V1 的 Schema 从 90% 提升到 100%，关键事实召回从 83.3% 提升到 95.6%，Evidence 有效性从 90% 提升到 100%。本次 V2 正式评测中，24 例有 23 例成功，医疗安全、跳过与未记录区分、行动白名单和无依据数字控制均达到 100%，但 Schema 和 Evidence 有效率是 95.8%，关键事实召回是 91.7%，因此我没有包装成发布通过，而是保留了 2 个 Bad Case：一个遗漏核心 Evidence，一个 Repair 后仍结构失败。人工固定抽检 12 例中 9 例四项全过。这个过程也发现评测 Runner 仍走旧同步接口以及评分器误判日期等问题，说明评测系统本身也需要校准，不能只看一个总分。

## 7. 高频追问与事实边界

### 为什么不用一个 LLM-as-a-Judge 全部评分？

客观约束优先使用确定性规则，成本更低、结果更稳定、失败原因也更容易解释。语义与体验指标再用人工抽检，当前样本规模不需要额外搭建 Judge 系统。

### 为什么只做 24 例 V2？

目标是校招级、可解释的最小闭环，优先覆盖高风险场景和 Bad Case，而不是堆数量。后续真实用户反馈会继续沉淀为回归案例。

### 为什么 P95 超过 30 秒也不直接判失败？

产品已改为异步任务。模型生成总时长仍需记录，但用户链路更应该评价任务创建、最终完成、刷新恢复和重复处理，而不是沿用同步接口的单一 30 秒门槛。

### 评测通过是否代表产品可以用于医疗决策？

不代表。评测只验证合成场景下的记录摘要质量和非医疗安全边界，不能证明诊疗效果，也不能替代医生。
